Schedule and Publish

Two departments that run back to back. Schedule owns time: when each approved deliverable goes out, on which platform and account. Publish owns the door to the platforms: one adapter that either hands the founder a ready composer or, once the owner decides, posts through Zernio at the approved time. Markdown twin for agents: schedule-publish.md. Parent pages: ai-cmo.html, approval.html. Status: proposed.

Verdict

Decided 2026-10-26: every platform through Zernio, X included

Owner's call, to keep it simple: one adapter for all scheduled posting. The founder connects each account once through Zernio's OAuth link; at the approved time the worker posts through Zernio, and a webhook confirms. Tokens stay with Zernio, we never build a platform app, and X goes the same way (Zernio passes X's API price through).

This is still "assist, never act": nothing goes out without the founder's approval of the content, the time and the account, on the founder's own account. It does change the copy from "you post it" to "you approve when it posts", so the landing and the cards must say that.

Before it ships
  • Check three things on Zernio: whether its TikTok app is audited (or TikTok posts go private), the real price per connected account, and its terms for a SaaS reselling posting.
  • The intent link stays only as a fallback for a founder with no connected account (or when Zernio is down): the notice opens a filled composer.
  • X API cost passes through: about $0.015 a post and about $0.20 for a post with a link.

Found in the code: there is no timezone anywhere for a founder. Scheduling at a time needs one first.

How a time is picked
  • Timezone first: a new profiles.timezone, set at onboarding from the browser and editable.
  • Default slots per platform from published studies (Buffer's 2026 data), stored as data, not code.
  • The founder's own data takes over once a platform has about 10 published posts with metrics: the slots with the best median views.
  • Gaps and caps: at least a few hours between two posts on one platform; a daily cap per platform in SQL (5 X approvals today).
  • A short and its long video are not posted on the same platform the same day.
  • A small agent is optional: the rules above are code; a model is used only to explain the pick in one line on the card.

The clock is Modal's sweep (every minute): it claims due slots with a lease and creates a publish work order or a reminder. A slot that is more than a set time late becomes missed and raises a new schedule card; it never posts late (Approval rule 4).

The calendar the founder already sees (the week plan) gains a time per item and drag and drop; moving an item changes the time and supersedes its card.

One function, publish(deliverable, slot), returns { status, external_id, url, error }, so the brain and the event rules never know which adapter ran.

Media goes from the worker straight to Zernio's presigned upload, never through Next.js (web rule 3). The worker reads the export from Storage with a signed URL.

Webhooks from Zernio land on a signed Vercel route, with a receipts table against replays (as Polar's webhooks do), and set the slot and deliverable status. A failure raises a card with the reason and a retry that reuses the same approval while it is still valid.

Connecting an account is the founder's own OAuth through Zernio's connect link, once per account; social_accounts stores the Zernio profile and account ids, the platform and the handle. Disconnecting removes them.

Build phases

  1. P0 · Zernio checks and account connect. The three checks (TikTok audit, price, terms); profiles.timezone; a Zernio profile per founder; social_accounts with connect and disconnect, X first (the account the owner posts from today).
  2. P1 · Scheduled posting through Zernio. A time on each calendar item; schedule_slots; schedule cards (Approval A3); sweep fires due slots into publish_post work orders; media uploaded from the worker; signed webhooks with receipts; TikTok's required fields on the card; the intent fallback for founders with no connected account.
  3. P2 · Best time. Default slots per platform as data; the founder's own slots once a platform has enough posts; jitter; gaps and caps.
  4. P3 · Metrics through Zernio. Zernio analytics for connected accounts next to today's public reading.

P1 needs Approval A0–A1 (one table, snapshot) and the schedule card of A3. The shorts and slideshows from Studio S2–S3 go out through the same path to TikTok, Reels and Shorts.

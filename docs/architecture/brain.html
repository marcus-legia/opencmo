§1

Verdict

Kept from before

  • One loop, many configurations: the CMO chat runs on the Assistant loop with its own scope (lib/agent/scope.ts).
  • One place that asks a model (jobs/think.ts), with two brains: our models, or the founder's own Claude through the inbox. No competitor we read has the second.
  • Steps logged before and after each call, leases, Deferred, credit hold per run, daily limits in SQL.
  • Three memory tiers with a Sunday summary (what Letta calls sleep-time compute).
  • Learning from the founder's edits (cmo_draft_outcomes, classify-edits.ts).

Added, and built

  • A work order tree with briefs, dependencies and budgets (work_orders).
  • A progress ledger: a daily, code-only check of the tree; a replan only when work is stuck (jobs/progress.ts).
  • A capability registry so the brain reaches Studio, Schedule and Publish through the same tools as buttons and MCP (packages/contracts/capabilities.json).
  • Event rules (SQL triggers), a weekly budget that is a hard gate with a cost ceiling, a kill switch, and a corrections log read first (cmo_corrections).

Not adopted, and still not: a multi-agent framework (CrewAI, LangGraph, AutoGen) or a hosted workflow engine (Inngest, Temporal, Vercel Workflow). The reliable part is code-owned control flow; the Postgres queue and Modal clock give durability; CLAUDE.md forbids a second runtime.

§4b

How the brain runs without a browser

Scroll sideways to see the whole diagram.

No machine stays on for the brain. Supabase holds every order and its state, Modal is the clock and the muscle, Vercel is where the brain thinks, and the browser is only the screen where the founder reads and approves. Closing the browser stops nothing the brain does.

hourly, at :05    Modal cmo_schedule ──GET──▶ Vercel /api/cron/cmo        loops due today → rows in the queue
every hour        Modal cmo_digest   ──GET──▶ Vercel /api/cron/cmo-digest  the morning digest in each founder's timezone
every minute      Modal sweep()      ──POST─▶ Vercel /api/internal/cmo/run  once per waiting order (≤ 10)
                                               answers 202, works in after(): claim with a lease, run steps,
                                               think(), write results; longer work defers
                                               itself (cmo_defer_run) and resumes on a later sweep
                  sweep() also: reclaims expired leases, closes stuck Assistant turns and open credit jobs
heavy work        Vercel ──submit──▶ Modal worker; worker claims rows in `tasks` with a lease
browser           reads cards and approves under RLS; when closed, cards wait in `waiting_founder`
founder's Claude  (claude brain mode) requests wait in `cmo_inbox` until it answers
WireWhat travels on itBuilt in
1 Rows in Postgresthe main wire: the brain inserts an order row with a brief; a department claims it with a lease, writes its result, changes the status; no agent calls another directlycmo_runs, work_orders, tasks, deliverables

3 Event rulesa trigger on status changes inserts the next order: edit finished → cut_shorts; short or post approved → Schedule; slot due → Publish; posted + 24 h → measureeditor_projects_rules, tasks_studio_rules, approvals_caption_rules, schedule_follow_deliverable, work_orders_follow_approval

Long work: the brain never waits on a machine.

  • A video order hands its brief to the Studio team and moves to waiting_order, holding no lease and no machine.
  • When the team's generations are done, the next sweep wakes the order (studio_steps_ready).
  • A card waits in waiting_founder as long as it takes; email and web push remind the founder.
  • A crash mid-step loses nothing: the lease expires, the order returns to the queue, logged steps replay.

The one part that needs a browser: the Assistant chat. When a turn hits its time or step limit, the open tab calls continue (awaiting_continue in lib/agent/loop.ts), and tools such as frame capture run in the tab. That is why the brain never drives the editor through a hidden chat: it calls the Studio team's entry points with plan / decide, which MCP also runs with no browser.

The step cut at 280 s (#178). The routes run on Vercel Hobby, where a request cannot pass 300 s: past it the platform kills the request with no answer, and the turn failed minutes later as "stopped responding" (2026-11-08, an explainer's scene code written in one step). A model step still streaming 280 s after its request started is cut (STEP_DEADLINE_MS in lib/agent/limits.ts), so the loop can still record the call and tell the model to go smaller; after MAX_LATE_STEPS (2) late steps in one turn it stops and says so. Whether to move to Vercel Pro is the owner's decision.

Compared with an agent kept alive in a cloud container per session, state lives in Postgres and compute wakes only when a row is waiting: idle costs nothing, a crash resumes from the last logged step, and there is no second runtime.

Work orders

Scroll sideways to see the whole diagram.

work_orders sits beside cmo_runs instead of replacing it (decision 3 below changed in the build): a run is still the job a department executes, and its order follows it. Schema as built:

id, user_id, root_id, parent_id, week (a Monday)
department      brain | research | writer | studio | sales | schedule | publish
kind            plan_week, post_draft, write_video_brief, build_video, cut_shorts,
                build_slideshow, build_post_image, write_caption, publish_post…
title, brief    { objective, output, sources, boundaries, done_when } (≤ 4 KB)
status          queued | running | waiting_founder | waiting_order | deferred
                | done | failed | cancelled
depends_on      uuid[]   (≤ 20, all must be done)
budget_credits, spent_credits
run_id → cmo_runs, item_id → content_items
created_by      loop | chat | event | mcp | founder
due_at, finished_at, done_reason
error           { code, message, … }

Rules (built):

  • One writer of status: an RPC per transition (work_order_move, work_order_wait_founder, studio_order_move); every change is logged in work_order_events.
  • Ends with an artifact: done needs a deliverable or a stated done_reason.
  • Children inherit the root's budget and cannot spend more than the parent has left (work_order_spend).
  • Paid or outbound children wait (waiting_founder) with the price shown.
  • A failure is data: the replan reads error.code and may not retry the same brief unchanged (work_order_mark_replanned).
  • Effort scales by kind: the registry sets steps and credits per kind.

States: queued → running; running pauses into waiting_founder, waiting_order or deferred (no lease held) and resumes when approved, answered or the timer fires; it ends done, failed or cancelled (rejected, over budget, kill switch). failed goes to the Planner for one replan with a new brief.

§7

Capability registry

packages/contracts/capabilities.json with capabilities.schema.json, checked by lib/cmo/capabilities.check.ts: every CMO job is listed once, a job's fixed price is the one SQL charges (cmo_job_price), the Studio adapter's entries have the callers STUDIO_ACCESS gives them, and every file that starts a CMO job or calls the Studio adapter must be listed as a caller. A new path (a private brain shortcut, a new route) fails the check until the registry says who it is.

  • effect: read | write | spend | outbound; approval: none | founder | price.
  • callers keeps the brain from a private path.
  • Tools stay where they are (editor-core ops, cmo-tools.ts, the Studio adapter); the registry only lists them.

§7b

Brain ↔ Studio: the brain briefs the Video agent team

Two levels of orchestration, as in Agent Opus: the brain plans the week and hands a brief to Studio; Studio's own agent team plans and makes the deliverable. The brain never drives single tools inside the team. Editing the founder's own video stays hands-on.

The Studio adapter (lib/departments/studio/adapter.ts) has eight entry points: plan, decide, buildVideo, cutShorts, markFinished, renderShort, buildSlideshow, buildPostImage (STUDIO_ENTRIES in types.ts). Callers: the brain's order runner, the Assistant chat, MCP. buildVideo and renderShort are the brain's; marking an edit finished is the founder's call only.

What the brain adds

  • The brain is the team's third caller. It sends a brief from the week plan; the adapter runs the squad and raises the same cards in the Approval inbox.
  • The work order waits in waiting_founder on a card and in waiting_order while generations run.
  • In claude brain mode the founder's Claude may write the Director's plan (as MCP allows); the code Reviewer checks it.

Rejected: the brain calling create_video itself (it skips the team; every pipeline change would break the brain) and a hidden Assistant chat (open loop, unpredictable cost, unseen cards). The team owns how a video is made; the brain owns what the week needs.

A brain video, in order (Brain · Studio agent team · Worker + fal · You). Since S2.5 the week plan orders none; the order kind stays for MCP and Studio:

  1. Video brief (write_video_brief) → build_video order → the order holds its team allowance (studio_order_hold).
  2. Director writes the plan; the Reviewer checks it; one price for the whole video: keyframes, shots, voice-over, music (nothing spent on media yet).
  3. Card 1: storyboard and that one price. 4. You approve: one job hold for the estimate (credit_orders).
  4. Every piece starts at once from the hold; each shot waits on the worker for its keyframes; the Builder places one scene.
  5. Generations done → the order resumes → render → look check.
  6. Card 2: the finished video, to open in the editor and tweak. Approving marks the edit finished.
  7. Event rule → cut_shorts → Card 3: the shorts batch; approved shorts go to Schedule with their captions.

History: the contact sheet card (once card 2) was removed on 2026-11-06 (charge before running, D9); one keyframe is changed after with redo_keyframe, at its own price. Its last leftovers (the redo branch, ContactSheet.tsx) were removed in S2.8 (814dbb7).

  • Security: the team runs under the founder's RLS session; a Studio order mints a short-lived user JWT as MCP does (brainClientFor); the service role never writes an editor document.
  • Money: the team's model calls are paid from the order's allowance (§9); keyframes, shots, voice and music from the job hold confirmed on card 1; the Shorts squad spends no generation credits; all count against the order tree's budget (studio_video_budget() = 60 for a video order).

§9b

What an Assistant turn costs

The CMO chat and the Editor Assistant run on the same loop (lib/agent/loop.ts), and a turn holds credits before it calls a model.

  • Overage is billed (20270109010000_agent_turn_overage.sql). A turn is billed for every credit it used. Until then the close charged least(hold, used), so a step that ran past the hold was free.
  • The explainer cap (20270110010000_review_fixes.sql). The plan_explainer card promises "writing and checking, up to agent_3d_hold_credits()" (20 credits). A turn that opened an explainer job is charged at most that for its tokens; past it, the cost is ours.
  • Stuck turns close. The sweep closes turns left running or waiting (agent_reap_turns) and, with them, credit jobs left open for a day (credit_orders_reap).

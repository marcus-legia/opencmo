The CMO brain

What the brain is today, what nine outside systems teach us, and the design we propose: a small LLM planner on top of deterministic code that owns dispatch, budgets and approval. Markdown twin for agents: brain.md. Parent page: ai-cmo.html. Status: proposed, nothing here is built yet.

Verdict

Keep
  • One loop, many configurations: the CMO chat already runs on the Assistant loop with its own scope (lib/agent/scope.ts).
  • One place that asks a model (think.ts), with two brains: our models, or the founder's own Claude through the inbox. No competitor we read has the second.
  • Steps logged before and after each call, leases, Deferred, credit hold per run, daily limits in SQL.
  • Memory in three tiers with a Sunday summary: this is what Letta calls sleep-time compute, already built.
  • Learning from the founder's edits (cmo_draft_outcomes, classify-edits.ts).
Add
  • A work order tree with briefs, dependencies and budgets, so one weekly plan becomes tracked work in every department.
  • A progress ledger: a daily, code-only check of the tree that triggers a replan only when work is stuck.
  • A capability registry so the brain can reach Studio, Schedule and Publish through the same tools as buttons and MCP.
  • Event rules, a weekly budget with a cost ceiling and a kill switch, and a corrections log the brain reads first.

Do not adopt a multi-agent framework (CrewAI, LangGraph, AutoGen) or a hosted workflow engine (Inngest, Temporal, Vercel Workflow). Every source below agrees that the reliable part is code-owned control flow; our Postgres queue and Modal clock already give durability, and CLAUDE.md forbids a second runtime.

Design: an LLM planner on top of code that owns the rest

Only two parts of the brain call a model: the Planner and the Reviewer. Dispatch, budgets, gates, event rules and the progress check are code, so they are cheap, testable and cannot be argued with.

4b

How the brain runs without a browser

No machine stays on for the brain. Supabase holds every order and its state, Modal is the clock and the muscle, Vercel is where the brain thinks, and the browser is only the screen where the founder reads and approves. Closing the browser stops nothing the brain does. Most of this already runs today.

Scroll sideways to see the whole diagram.

WireWhat travels on itState
1 · Rows in PostgresThe main wire. The brain gives an order by inserting a row with a brief; a department takes it by claiming the row with a lease, writes its result and changes the status. No agent calls another agent directlybuilt (cmo_runs, tasks, leases)
2 · HTTP with a secretModal → Vercel (CRON_SECRET) to wake the brain; Vercel → Modal submit (worker token) to start heavy work at once; MCP → worker wake (a token that can do nothing else)built
3 · Event rulesA trigger on status changes inserts the next order: video approved → cut_clips; clip approved → Schedule; posted + 24 h → measurenew
Long work: the brain never waits on a machine
  • A video order hands its brief to the Studio team and moves to waiting_order; it holds no lease and no machine.
  • The worker makes keyframes and shots; when the team's generations are done, the next sweep sees it and wakes the order (new: one more check in sweep).
  • A card waits in waiting_founder for as long as it takes.
  • A crash mid-step loses nothing: the lease expires, the order goes back to the queue, the logged steps replay.
The one part that needs a browser

The Assistant chat in the editor. When a turn hits its time or step limit, the open tab calls continue (awaiting_continue in lib/agent/loop.ts), and tools such as frame capture run in the tab. Close the tab mid-turn and the turn waits.

That is why the brain never drives the editor through a hidden chat. It calls the Studio team's entry points with plan / decide, which MCP already runs with no browser at all.

Compared with "an agent always on in the cloud" (one container kept alive per session), this keeps all state in Postgres and wakes compute only when a row is waiting: idle costs nothing, a crash resumes from the last logged step, and there is no second runtime.

Work orders

work_orders grows out of cmo_runs; existing kinds keep working. The brief follows Anthropic's subagent brief and ai-cmo-operator's "ends with an artifact" rule; failures follow Agent Opus's structured last_failure.

Row 
id, user_id, root_id, parent_id
department      research | writer | sales | studio
                | schedule | publish | brain
kind            plan_week, post_draft, write_script,
                build_video, cut_clips, schedule_slot,
                publish_post, check_progress…
status          see the state machine
brief           { objective, output, sources,
                  boundaries, done_when }
depends_on      uuid[]   (all must be done)
budget_credits  spent_credits
deliverable_id  → deliverables
brain           opencmo | claude
created_by      loop | chat | event | mcp | founder

error           { code, message, retryable,
                  repair_hint }
Rules
  • One writer of status: an RPC per transition, so a job cannot mark itself done without a deliverable.
  • Ends with an artifact: done needs a deliverable_id or a stated "nothing to do" reason.
  • Children inherit the root's budget; a child cannot spend more than its parent has left.
  • Paid or outbound children wait (waiting_founder) until approved, with the price shown, like Higgsfield's spend approval.
  • A failure is data: the replan reads error.code and repair_hint and may not retry the same brief unchanged (Opus's duplicate guard).
  • Effort scales by kind, not by the model's mood: the registry says how many steps and credits a kind may use.

Capability registry

One JSON file in packages/contracts, checked by check:contracts like task-kinds.json. Each entry says who may call it and what it costs, so the brain, buttons, the Assistant and MCP all see the same list. This is the bridge to Studio that is missing today.

Entry 
{
  "name": "build_video",
  "department": "studio",
  "effect": "spend",        // read | write | spend | outbound
  "approval": "price",      // none | founder | price
  "callers": ["brain", "ui", "assistant", "mcp"],
  "order_kind": "build_video",
  "max_steps": 40,
  "credits": "quote",       // fixed number or quote
  "input": "BuildVideoInput" // zod schema name
}
Why this shape
  • effect + approval come from Claude Code's read-only / destructive tool flags and the Vercel AI SDK's per-input tool approval (our reading notes in the internal repo).
  • callers keeps the brain from getting a private path (rule 3 of ai-cmo.html).
  • max_steps and credits are the effort budget Anthropic puts in the prompt; we put it in data, where code can enforce it.
  • Tools stay where they are (editor-core ops, cmo-tools.ts); the registry only lists them.

7b

Brain ↔ Studio: the brain briefs the Video agent team

Two levels of orchestration, the way Agent Opus does it: the brain plans the week and hands a video brief to Studio; Studio's own agent team plans and makes the video. The brain never drives single tools inside the team. It talks to Studio for two jobs: an AI long video, then short clips cut from it. Editing the founder's own video stays hands-on in the editor.

Scroll sideways to see the whole diagram.

What is already built
  • Long take (/video, PR #111 on main): Director → code Reviewer → keyframes → contact sheet → shots between keyframes → one editable scene. Learned from Agent Opus: keyframes first, two approval cards, model chain by quality, prompt rules for shots.
  • Intro team (plan_video, lib/agent/video-team.ts): Writer, Motion director, code Reviewer, Builder.
  • Team members are agents in the registry (director, writer, motion, captions, moderation), so each switches provider by env like every CMO agent.
  • Three callers already share the team: the Assistant chat, and MCP (packages/mcp-server/src/groups/studio.ts), which runs the team's entry points without a chat by splitting each priced one into plan (nothing spent) and decide.
  • Open in the long-take plan: the real-model baseline (Tasks 0–1), the acceptance video (Task 8) and the release.
What the brain adds
  • The brain is the team's third caller, next to the Assistant and MCP. It sends a video brief (topic, audience, length, frame, voice) from the week plan; the team's lead (the pipeline runtime) runs the squad and raises the same cards.
  • The cards land in the Approval inbox instead of the chat. The work order waits in waiting_founder on a card and in waiting_order while the team's generations run.
  • In the claude brain mode the founder's Claude can write the Director's plan, as MCP already allows; the code Reviewer checks it either way.
  • New squad: Clips. Clip editor (LLM), Clip reviewer (code), Builder (make_clip op), Renderer. It runs only on an edit the founder marked finished.
Rejected: the brain driving tools one by one, or a hidden chat

The first version of this section had the brain call create_video and animate_video itself. That skips the team: the brain would need to know keyframes, shot models and redo rules, and every change to the pipeline would break it. A hidden Assistant chat ("make this week's video") is worse: an open loop with unpredictable cost and cards nobody sees. The team owns how a video is made; the brain owns what video the week needs.

Loading rule: a work order's brief names the documents and topics it needs, and the job loads only those (ai-cmo-operator loads 2–5 of 10 files; Anthropic calls this just-in-time retrieval). Corrections and the profile are the only tiers every job reads.

Where corrections come from: classify-edits.ts already labels each edited approval. The Sunday summary turns repeated labels into a proposed correction; the founder approves it as a card. Hermes Agent lets skills rewrite themselves; we keep that behind approval.

Not now: vector search. Topic filtering is enough until a founder passes about 200 memory rows (the old handoff doc set this threshold).

The Library: shared knowledge the brain reads but does not own

Owner decision, 2026-10-27. What belongs to the business lives in one Library that the brain and every department read. The brain keeps only what it produces itself.

Reasons: departments also run without the brain (the editor, the founder's own Claude through MCP), each thing has one copy the founder edits in one place, and briefs stay small because a brief names what to load.

Not in the Library: the department playbooks in lib/cmo/skills/ (x-writing.md, reddit-listening.md, short-video.md, the marketingskills library/ folder…). They are how each department does its job, shipped and versioned by us, so they stay with the department; the Library shows only what the founder can change. UI: one Library page with four tabs (Business, Brand Kit, Voice, Skills). Research keeps insights; Writer shows the voice it uses and links to the Library.

11

Build phases

  1. B0 · Corrections + budget fields. Add tier 0 memory and a weekly budget on the profile; no new tables for orders yet. Small; useful the day it ships.
  2. B1 · work_orders from cmo_runs. Migration that adds the columns (root, parent, department, brief, depends_on, budget, deliverable, error) and keeps every existing kind running; plan_week writes a tree. pgTAP for every transition RPC.
  3. B2 · Progress check + kill switch + morning digest. Code only, runs in the daily cron; one replan for stuck orders.
  4. B3 · Capability registry, event rules, Studio adapter. The registry file and its check; event rules as a trigger table; build_video and cut_clips through the shared Studio adapter (section 7b), every paid step behind a card.
  5. B4 · Brain evals. 20 real profiles, plan judge, the measures above on the dashboard.

Each phase gets its own plan in docs/plans/ before code, as CLAUDE.md asks. B0–B2 do not touch the editor, so they do not compete with the editor roadmap; B3 is where the brain meets Studio.

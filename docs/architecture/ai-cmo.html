The CMO brain and its departments

OpenCMO is one CMO brain that plans and dispatches work to seven departments, with the founder approving everything that goes out. The departments are the product, so the system is shaped around them, not the other way round. It stays one system: Vercel + Supabase + Modal. Markdown twin for agents: ai-cmo.md. This page replaces the PR #117 diagram page and docs/cmo-architecture-implementation.md; ARCHITECTURE.md §11 still describes the CMO as built today.

  1. 1HTTPS: UI and API v1, session cookie, reads under RLS.
  2. 2TUS straight to Storage with a reservation; downloads by signed URL. Files never pass through Next.js.
  3. 3Writes through owner-checking RPCs; holding credits and creating work in one transaction.
  4. 4submit: Vercel calls Modal when the user clicks. If it fails, sweep claims the task within a minute.
  5. 5The worker claims tasks with a lease, writes results, reads and writes files with the service role.
  6. 6Modal is the only clock: cmo_schedule, cmo_runs dispatch and cleanup call Vercel routes.
  7. 7The founder's Claude connects to MCP with an API key (paid plans).
  8. 8MCP reads and writes under RLS with a 5-minute user JWT; it wakes the worker through wake.
  9. 9Posting today: the browser opens an intent link and the founder taps post.
  10. 10Polar webhooks into Vercel, with a receipts table against replays.
  11. 11Proposed: a publish_post task calls Zernio at the approved time, only while the approval is still valid.

What the PR #117 system diagram got wrong

  • Three stacked boxes with one-way arrows hid four direct paths: TUS to Storage, submit to Modal, Modal calling back into Vercel, the browser opening x.com.
  • The MCP server was a line inside the worker; it is its own Modal app (packages/engine/mcp_app.py) with its own secret. apps/web/app/api/mcp only answers 410.
  • "Cron runs CMO jobs" on Modal: Modal only keeps time; CMO jobs run on Vercel.
  • "Gemini: frame moderation": moderation.py uses the moderation agent in CMO_LLM_PROVIDERS order plus fal's NSFW classifier.
  • Supabase as one box: no queues (tasks, cmo_runs), no tables per department; week plans and drafts were placed in Storage instead of Postgres.
  • Clipping and "Writer → script → Assistant" were drawn as running; neither exists today.

9

Six rules that let the brain run every future feature

1 · One kind of work order

Everything the brain hands out is a work_orders row with a kind, a brief, a credit budget and a machine-readable failure. A new feature is a new kind and a handler, the way task-kinds.json works for the worker.

2 · One data spine

Every output is a deliverables row with kind, parent_id (the clip of a video, the caption of a video) and editor_project_id. One set of statuses for every department.

3 · One capability registry

A department's capabilities are tools. The brain, buttons, the Assistant and MCP call the same tool, the way editor-core is the editor's only write path. The brain gets no private path.

4 · Gates live on the write path

Ownership, credit holds and limits run inside database RPCs; moderation runs on the web and on the worker. The brain, buttons and MCP all pass through them, so a new department gets every gate without new code.

5 · The brain never posts

The brain reaches Publish only through Approval. The time is part of what the founder approves; editing the content, the time or the account needs a new approval.

6 · Every department has an eval

Writer has code + model evals (lib/cmo/jobs/eval), the editor 22 agent tasks (agent:eval). A new department arrives with its eval, measured by how often the founder approves as is.

11

Build order, in step with the editor strategy

  1. Writer: No AI Slop + per-platform captions. Small, no migration.
  2. The spine: work_orders, deliverables, department folders (changes 1, 2, 9). Before any new department; renames through migrations with pgTAP, keeping the data.
  3. Registry + Studio takes a script (3). v1: the brain writes the script, the founder clicks "Build" to open the Assistant. Fully headless (4) once the cost of one video is measured.
  4. One approval inbox, notifications, Schedule (5, 6, 7). Scheduled posting through Zernio at the approved time (owner decision 2026-10-26; see schedule-publish.html).
  5. Studio: slideshow, clips from a finished edit. With E4.1 of the editor roadmap.
  6. Publish adapter on Zernio for every platform (8), after the Zernio checks (TikTok audit, price, terms).
